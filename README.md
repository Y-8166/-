# 信息图形：数据逻辑 × 类型案例知识库

> 状态：**v0.1.0 基础框架（2026-11-19）**。当前未获得本项目的案例图片，因此所有概念说明均属**待案例检验的理论初稿**，不能充当具体作品的实证分析。

本仓库研究的对象是具有**数据/信息组织、视觉编码、阅读路径、叙事意图**的信息图形（infographics）。目的是从用户持续提供的案例图中归纳结构性规律，并在真实证据积累后更新分类概念、视觉设计原则和制作方法。

## 两套分类轴：不可混为一谈

| 层次 | 回答的问题 | 当前分类 | 位置 |
| --- | --- | --- | --- |
| **数据逻辑**（结构轴） | 数据为什么被这样组织，关系的本质是什么？ | 编年、层级、编目、字母表、地理 | [`01-信息图形数据逻辑/`](01-信息图形数据逻辑/) |
| **表现类型**（呈现轴） | 作品如何把信息转化为可阅读、可叙事的页面？ | 混合型、文字/列表型、时间轴型 | [`02-信息图形类型案例/`](02-信息图形类型案例/) |

**多对多关系**：一份时间轴作品常采用编年数据逻辑，也可能以地理或层级信息为辅；混合型作品可以叠加编目、地理和编年逻辑。不能仅凭画面形态判断数据的本质，也不能把“时间轴型”等同于“编年型”。

## 每收到一张案例图的更新程序

1. **登记来源**：分配不可变 ID（`CASE-0001` 起）；记录图片出处、作者/机构、时间、用户提供时间、版权及是否有可核验数据。
2. **先描述后推断**：客观抄录可见文字、数量、轴、单位、比例、布局、图形、阅读顺序。猜测或无法辨认的部分标记 `待核实`；不编造数值。
3. **双轴编码**：判别 1 个主导的数据逻辑（必要时附多个次级逻辑）及 1 个主表现类型（必要时附次类型），说明判定依据与可能的替代解释。
4. **沿 A–E 深描**：识别数据表结构、图表与公式、视觉变量、信息架构、叙事组织；截取具体可观察证据，区分“观察事实 / 解释 / 建议”。
5. **更新案例类型文件**：新特征登记到对应类型说明的“案例验证表”；样本不足时不将单一案例升格为通用原则。
6. **更新数据逻辑文件**：只修改被案例证据支持的条目；通过有效的相对 Markdown 链接指向 `02/案例记录/` 中的实例。`01/` 永远不放图像。
7. **保留修订依据**：在文档修订记录中写明日期、CASE ID、变更类型（新增/修订/反例/撤回）和理由；提交 Git 变更。

> “实时更新”在本项目中指**每次新增案例并进行分析后即更新知识文档**，而非没有触发条件的后台自动写作。仓库加入了自动链接与目录校验，提交时会检查结构；是否采纳概念修订仍需以案例证据判断。

## 研究与设计共通规则

- **可核算**：统计图形应标注指标、单位、分母、统计时间窗、数据来源，必要时列出公式。
- **结构与编码配合**：先确定数据关系，再选择位置、长度、角度、面积、颜色、图标及布局；装饰不能替代定量编码。
- **防止语义偷换**：把等级误写为时间、把枚举误写为排名、把地理面积误当数据量，均属于错误编码。
- **证据等级**：`理论假设` → `单例观察` → `跨例反复出现的模式` → `具有反例边界的设计原则`。不要跳级。
- **异议与反例**：为相反案例保留解释和修正规则，不能只收集支持已有分类的作品。
- **版权与隐私**：只有在具有适当使用权、授权或研究用途许可时才上传原图；记录出处，必要时仅保存链接。
